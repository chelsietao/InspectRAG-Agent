# 第四階段：生成回答與代理工具呼叫

這個階段把圖片分析、正常圖片搜尋與文件搜尋接到 Groq 的語言模型，使用者可以用一句話提出需求，由代理（Agent）選工具、取得資料，再產生附引用的結論。

第一版提供命令列介面（Command-line Interface，CLI），案件資料庫、跨對話記憶、網頁介面與模型上下文協定（MCP）尚未串接，這些功能會在後續階段增加。

## 這一版實際怎麼運作

例如使用者問「異常分數可以當成瑕疵機率嗎」，模型會提出文件搜尋工具的呼叫要求，程式執行本機檢索後，把段落與來源交回模型，再由模型提交帶引用的結構化回答（Structured Output）。

若使用者提供瓶子圖片並要求分析，圖片模型在本機計算分數與熱圖，正常參考圖也由本機索引搜尋，Groq 取得的是問題、數值、參考圖資訊與文件摘要，這版沒有把原始圖片上傳給語言模型。

### 可用工具

| 工具 | 負責什麼 | 可以取得的證據 |
|---|---|---|
| `analyze_image` | 分析使用者選取的圖片 | 分數、門檻、模型雜湊與熱圖 |
| `search_reference_images` | 搜尋最多 3 張正常參考圖 | 正常圖片編號與相似度 |
| `search_documents` | 搜尋最多 3 段文件全文 | 段落、標題與來源網址 |
| `read_evidence` | 補讀本輪已搜尋到的段落 | 原段落與出處 |
| `submit_answer` | 提交最終回答 | 狀態、帶引用結論、限制與補充問題 |

圖片工具只接受 `selected-image`，對應使用者透過 `--image` 選取的檔案，模型無法指定任意本機路徑，文件工具也只能讀本輪已檢索的段落。

## 模型與費用怎麼處理

目前供應商固定為 Groq，模型固定為 `qwen/qwen3.8-27b`，這個模型列於查閱當時的[官方免費方案用量表](https://console.groq.com/docs/rate-limits)，工具能力可參考[官方工具呼叫說明](https://console.groq.com/docs/tool-use/overview)。

程式不會更換供應商、切換其他模型或升級帳號，SDK 自動重試（Automatic Retry）設為 0，收到 `429` 就回傳 `rate_limited` 並結束本次執行。

免費方案（Free Plan）取決於 Groq 帳號設定，模型清單 API 無法驗證帳號的計費層級，因此程式中的 `plan_expectation: free` 是使用限制設定，帳號仍需維持免費方案，日後若自行升級，API 呼叫可能依平台規則計費。

本專題不需要設定 OpenAI API 金鑰，Groq 金鑰透過環境變數（Environment Variable）`GROQ_API_KEY` 或本機 `.env.local` 讀取，檔案已由 Git 排除，程式也不輸出金鑰內容。

## 限制怎麼落實

| 限制 | 本版設定 | 超過時怎麼處理 |
|---|---|---|
| API 次數 | 每次執行最多 5 次 | 回傳 `api_call_budget_exceeded` |
| 工具次數 | 每次執行最多 8 次，包含最終提交 | 回傳 `tool_budget_exceeded` |
| 每次輸出上限 | 900 個文字計算單位（Token） | 依模型回傳與結構檢查處理 |
| 對話內容大小 | 訊息與工具定義合計最多 22,000 字元 | 回傳 `context_budget_exceeded` |
| API 等待時間 | 30 秒，停用自動重試 | 回傳逾時或連線錯誤 |
| 結構修復 | 最多一次 | 再失敗就回傳 `validation_error` |
| 文件與參考圖片候選 | 每次最多 3 筆 | 由參數驗證擋下 |

字元上限是目前的上下文預算（Context Budget），實際 Token 用量另外保存，兩者沒有固定的一比一關係，免費方案也有每分鐘與每日限制，單次執行上限無法取代平台配額。

### 本輪證據如何隔離

每次執行會清空證據、已讀段落與工具快取（Cache），每個代理執行個體只接受一輪問題，下一輪需重新建立執行個體，避免把上一輪來源當成本輪已取得的資料。

最終回答中的每項結論都要有本輪有效的證據識別碼（Evidence ID），程式會擋下不存在的引用、未知工具與額外欄位，文件中的指令也只作為待閱讀資料。

這些檢查驗證的是結構與來源編號，結論是否與引用段落的意思一致，仍需要主張支持度（Claim Support）評估與人工審閱，程式不會把引用合法當成事實查核完成。

## 回答長什麼樣子

結果的 `status` 描述本次執行狀態，`answer.claims` 保存帶引用的結論，`limitations` 說明限制，`citations` 由程式根據本輪證據組成，來源網址不交給模型自行編造。

| 狀態 | 意思 |
|---|---|
| `answered` | 已產生通過結構與引用編號檢查的回答 |
| `needs_context` | 需要使用者補圖片或資訊 |
| `insufficient_evidence` | 現有資料不足以支持要求 |
| `rate_limited` | 平台限制用量，本次停止 |
| `provider_error` | 憑證、連線或模型請求發生錯誤 |
| `validation_error` | 回答格式或引用仍不符合規則 |
| `stopped` | API、工具或內容大小達到上限 |

`answered` 不代表產品已通過品質檢驗，模型分數也無法替代產品允收標準，製程根因、修復處置與出貨決策需要額外的合格資料與專業判斷。

## 在 VS Code 執行

在專案根目錄開啟終端機（Terminal），可以先檢查金鑰是否已設定，線上檢查只查詢模型清單，不會產生回答。

```bash
.venv/bin/python scripts/check_groq_setup.py
.venv/bin/python scripts/check_groq_setup.py --online
```

文件問答可以從下列問題開始，結果預設存到新的本機執行資料夾。

```bash
.venv/bin/python scripts/run_agent.py "異常分數可以當成瑕疵機率嗎，請查文件並附來源。"
```

需要圖片分析時，加上圖片位置，模型只會透過已選取的圖片編號執行工具。

```bash
.venv/bin/python scripts/run_agent.py "請分析選取的瓶子圖片，找三張正常參考圖，並查文件說明分數與判斷的限制。" --image bottle/test/broken_large/000.png
```

也可以指定儲存位置，輸出需位於專案 `artifacts/` 下方，既有資料夾會保留並停止覆寫。

```bash
.venv/bin/python scripts/run_agent.py "目前資料能判斷製程根因嗎" --output artifacts/my_agent_run
```

每次會產生 `result.json` 與 `answer.md`，有執行圖片分析時也會保存分析數值和熱圖，這些執行檔案保留在本機，公開報告只收錄挑選過的公開資料範例。

## 程式測試與真實 API 測試分開

程式測試使用模擬回傳（Mock），檢查未知工具、引用錯誤、缺圖、資料不足、格式修復、上下文限制、跨輪引用、`429` 停止與憑證錯誤，不需要 API 金鑰，也不會使用平台額度。

真實 API 測試則採少量公開資料案例，保存實際工具順序、模型名稱、Token 用量與回答，遇到額度限制就記錄狀態並停止，沒有重試到成功才隱藏失敗的機制。

```bash
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m pip check
```

本階段測試不等同完整的代理品質基準（Agent Benchmark），後續仍需固定更多問題、檢查主張支持、工具選擇與不足處理，再報告任務成功率。

## 安裝依賴與重現

其他電腦需先完成資料、視覺與檢索階段，再安裝代理依賴（Agent Dependencies），金鑰由使用者自行保存在當地環境，公開設定範例只提供空白欄位。

```bash
.venv/bin/python -m pip install -r requirements-agent.txt
```

模型設定放在 `configs/agent.json`，提示版本（Prompt Version）放在 `prompts/inspection_agent_v2.txt`，回答紀錄保存提示雜湊與使用量，方便檢查設定變動。

| 測試 | 結果 | API 次數 | 工具流程 |

| 圖片代理 v1 | 遇到免費額度限制並停止 | 4，包含被拒絕的請求 | 分析、參考圖與文件完成，補讀介面不一致 |
| 圖片代理 v2 | 已產生附引用回答 | 2 | 分析、參考圖、文件與最終提交 |

第一次圖片流程讓我發現，文件搜尋回傳的證據編號有 `doc:` 前綴，補讀工具卻期待另一種編號，模型因此多繞了幾步，之後也碰到 `429`，本次保留未完成紀錄並修正介面，沒有把限流算成成功。

修正後，補讀工具接受搜尋回傳的完整證據編號，提示版本也提醒模型在已取得全文時直接提交，新增測試檢查同一個編號能從搜尋接到補讀，也確認無法補讀尚未取得或非文件的證據。

新版圖片案例的分數為 19.4798，固定門檻為 10.1945，工具判為異常，正常參考圖為 `196.png`、`023.png` 與 `208.png`，產生的回答也說明分數不代表瑕疵機率，案例只用於確認流程，不能當作廣泛任務成功率。

已完成的完整程式測試共 50 項，其中代理與工具介面相關測試 26 項，缺圖、資料不足與未知工具等分支以模擬回傳驗證，這些分支尚未形成獨立的真實模型評估集。
